Run it in two minutes

Quick start.

The tool itself lives in rca-mas/. It is self-contained — drop the folder anywhere and run it.

# 1. Go to the repo you want to analyze cd /path/to/your/repo # 2. Run the pipeline against a bug report bash /path/to/rca-mas/rca-mas.sh /path/to/bug.md # 3. Read the report cat .rca-mas/runs/latest/report.md

To try it immediately against the bundled example, see rca-mas/run.sh — bash run.sh run runs against rca-mas/examples/bug.md inside the tool's own folder.

How the pieces connect

The pipeline at a glance.

A note for whoever picks this up

Built with Claude Code — and Claude Code can keep building it.

Every piece of this repo — the orchestrator, the collectors, the prompts, the tests, even these three HTML walkthroughs — was written with Claude Code as a collaborator. The same workflow is available to whoever inherits this work.

⌘

The tool reads its own instructions

rca-mas/CLAUDE.md and the root CLAUDE.md are written for Claude Code to consume. They define the architecture lock, the safety rules, the path conventions, and a what-to-change-where map. Open the repo in Claude Code and ask "explain the pipeline", "add a new collector for <X>", or "why does Agent 1b have a repair prompt?" — Claude Code already has the map.

→

Practical things Claude Code can do here

Diagnose a bug end-to-end via rca-mas.sh. Author or refine prompts in rca-mas/prompts/. Add a collector by following rca-mas/docs/development-guide.md. Run the test suites (bash run.sh test-fast, then test, then test-real-repo) and triage failures. Update docs in step with code changes — that's the project rule.

For chat-driven use inside any target repo, append rca-mas/templates/CLAUDE.md.snippet to that repo's CLAUDE.md and prompts like "use rca-mas to find the issue in bug.md" just work.

Inviolate rules

What the tool will never do.

These guarantees are enforced by rca-mas/.claude/settings.json — not by convention.

  • Never commit, push, tag, or open a pull request.
  • Never edit files in your working tree. --validate works in an isolated git worktree, then deletes it.
  • Never read .env, .pem, .key, id_rsa, or any credential file.
  • Never run curl, wget, ssh, or scp.
  • Never scan its own folder when analysing a different target repo (rca-mas/** and .rca-mas/** are excluded).

Full trust model in rca-mas/docs/security-model.md.

For my successor

One paragraph for whoever inherits this.

The architecture is intentionally locked. Five pipeline stages, four collectors, four schemas, two CLAUDE.md files, sixteen reference docs. The lock is not because the design is perfect — it's because a moving target was the single biggest risk during the build. New ideas live in potential_changes.md and on the improvements walkthrough. When you're ready to extend, unlock deliberately: read rca-mas/docs/decisions.md first to understand what was already considered and cut. Then change the architecture doc in the same commit as the code. The rule that has saved this project the most pain is the one at the top of rca-mas/CLAUDE.md: when you change code, update the matching doc in the same step.

✓

The shortest possible onboarding path

Day 1. Read this page. Open all three walkthroughs. Clone pallets/click into test-repos/click/. Run bash run.sh test-fast inside rca-mas/. Read the resulting report.md.

Day 2. Read rca-mas/docs/index.md and follow the order it gives you. By the end of the day you will have read every doc that matters.

Day 3. Pick one item from the improvements walkthrough that is small enough to ship in a week. Discuss with Claude Code before touching code. Update the doc in the same commit.
