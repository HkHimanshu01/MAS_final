1
Intake: the bug arrives
Bash · No AI
A QA tester writes a bug report (a bug.md file, a GitHub Issue, or a pasted stack trace). The entry script rca-mas.sh receives it, validates that prerequisites are in place (git, jq, claude), treats the bug text as untrusted input, and opens a clean run folder under .rca-mas/runs/<RUN_ID>/. No AI is called. No code is read. Takes about 1 second.
Entry point
rca-mas.sh
You can change
How the bug report is passed in. Add new input modes.
Output
bug.md + manifest.json in the run folder
What you can't break
The run folder creation . Everything else reads from it.
2
Briefing: bash scans the repo before the AI starts
Bash · No AI
Four bash scripts run in parallel against the target repo. They are called "collectors". Each one extracts one type of information and writes it into briefing.md. This file is what the AI agents read first . It saves them 8 to 12 turns they would otherwise spend exploring the repo from scratch. No AI is called here. No code is modified.
Main script
scripts/briefing.sh
Collectors
collectors/git.sh, deps.sh, errors.sh, testrunner.sh
Output
briefing.md + errors.txt
Tunable
RCA_GIT_LOOKBACK, RCA_ERROR_GREP_LIMIT, RCA_COLLECTOR_TIMEOUT
💬
Not sure? Ask Claude
If you want to add support for a new programming language to the import-tracing collector, just ask: "Add Ruby import tracing to collectors/deps.sh. Look at how Python is handled and follow the same pattern." Claude will read the existing code and write the new case for you.
3
Diagnose: Agent 1a investigates, Agent 1b writes the verdict
Agent 1a + 1b · AI
Agent 1a (the investigator) reads the briefing and uses tools (Read, Grep, Glob, git commands) to explore the codebase. It fills in a structured ledger every turn: current hypothesis, evidence, confidence, next action. Before stopping it must pass 3 mandatory checks: re-read cited files from the actual working tree, challenge its own conclusion, and justify its confidence score with a concrete observation count.

Agent 1b (the synthesiser) then reads the investigator's checkpoint and converts it into a schema-validated diagnosis.json. the clean, structured verdict that travels to the next stage.
Investigator prompt
prompts/investigation.md
Checkpoint format
prompts/investigation_write.md
Synthesiser prompt
prompts/diagnosis.md
Output
diagnosis.json. schema-validated, includes confidence score
4
Fix: Agent 2 writes the code change
Agent 2 · AI
Agent 2 reads the diagnosis and the verbatim current code of the fix location (carried in the fix_context field of the diagnosis). It proposes a unified diff: a precise, line-by-line description of the change. It never sees the full repo. If confidence is below the threshold (0.5 by default) it returns NO_FIX instead of guessing.
Prompt file
prompts/solution.md
Output
solution.json + patches/fix.diff
Threshold
RCA_CONFIDENCE_NOFX=0.5 in defaults.env
Weak-evidence band
0.5–0.6 → fix ships, flagged for review. ≥0.6 → normal fix.
5
Verify: Agent 2.5 proves the fix in an isolated copy
Agent 2.5 · AI + Bash
Only runs with the --validate flag. Bash creates a sibling git worktree (a temporary isolated copy of the repo) and applies the patch. The existing test suite runs. Then Agent 2.5 is called once to generate one targeted regression test. The orchestrator applies that test and runs it. Each step gates the next. If anything fails, the chain stops and reports honestly. The developer's actual repo is never touched.
Prompt file
prompts/validation.md
Output
validation.json + patches/generated_test.diff
Test timeout
RCA_AGENT25_TEST_TIMEOUT=1200 (20 min)
Total budget
RCA_AGENT25_TIMEOUT=1800 (30 min)
6
Report Creation: all artifacts assembled for the developer
Bash · No AI
scripts/report.sh reads every JSON file produced by the previous stages and assembles a human-readable 11-section report.md. The developer reads it in about 90 seconds: root cause, confidence, evidence, proposed diff, validation status, next action. This script never calls the AI and never modifies source code.
Script
scripts/report.sh
Output
report.md + cost_summary.json

How Testing Works

The system has 5 test suites. The first four are synthetic tests: they check that all the parts of the pipeline connect correctly without calling the AI or spending money. The fifth tests quality on real bugs from a real open-source project. You can run all four synthetic tests in under 10 minutes.

The 5 test suites: what each one checks

test_briefing.sh
Briefing end-to-end
Creates a tiny controlled repo and checks that briefing.md is produced correctly, has the right sections, and that error strings and file paths are extracted properly.
bash run.sh test-briefing
test_collectors.sh
Each collector individually
Checks git.sh, deps.sh, errors.sh, testrunner.sh each in isolation. Edge cases: empty input, excluded directories, unsupported language.
bash run.sh test-briefing
test_json_schemas.sh
Schemas and JSON helpers
Validates that sample JSON fixtures pass their schemas. Checks the JSON extraction helpers in lib/json.sh. Takes ~5 seconds. No Claude, no repo.
bash run.sh test-schemas
test_smoke_report_only.sh
Full pipeline wiring
Runs the entire pipeline using fixture JSON (no real AI calls). Checks that all output files are created, report.md has 11 sections, and the pipeline exits 0.
bash run.sh test
test_real_repo_briefing.sh
Quality on real GitHub bugs
Runs the briefing against 5 real bugs from the pallets/click Python library. Each bug has a known fix commit. The test checks that briefing.md surfaces the right files, that the error strings match real code locations, and that the test framework is detected. This is the quality gate . If briefing is broken, Agent 1a gets useless context. Requires the click repo to be cloned at C:/MAS_final/test-repos/click (or wherever RCA_REAL_REPO_ROOT points).
bash run.sh test-real-repo

What "real repo testing" means

The click fixture contains 5 real bugs that were filed as GitHub Issues and fixed by the pallets/click maintainers in real commits. For each one we have the original bug report (as bug1.md through bug5.md) and the expected output (which file should appear in the diagnosis, which commit introduced the bug, etc.).

Here is an example. Bug 1 is titled "Error hint shows env var when one doesn't exist". The bug report is a real GitHub issue from a real user. The agent is expected to diagnose it, identify src/click/core.py as the affected file, and propose removing the incorrect env var display from the error message.

tests/real_repos/click/bugs/bug1.md (first few lines)
# Error hint shows env var when one doesn't exist

#2696 added the environment variable to the error hint when
`show_envvar` is set. However, it does not check to see if
an `envvar` exists.

$ python ./click-test.py --bar aaa
Error: Invalid value for '--bar' (env var: 'None'): 'aaa' is not valid...
⚠️
Change carefully
The real-repo tests call Claude and cost real money (~$1–2 per full run across 5 bugs). Use bash run.sh test-real-repo-quick to run only bugs 1 and 4 for a faster $0.40 sanity check. Only run the full suite before declaring a major change complete.

Clone the repository you want to test against
Open a terminal and run: git clone https://github.com/owner/repo /path/to/local/repo . For example, git clone https://github.com/django/django /tmp/django. You only need to do this once.

Write a bug report as a plain text file

Add the bug as a formal test fixture (optional)
Copy the bug report into rca-mas/tests/real_repos/<your-repo>/bugs/bug1.md. Create a README.md in that folder describing the repo and the known fixes. ✦
Claude will write the test fixture for you
After you have run the agent on your new repo and seen reasonable output, paste the report into Claude and say: "Create a real-repo test fixture for this. Use the pallets/click fixture as the template. The repo is at /path/to/repo." Claude will create the directory structure, write the expected output JSON, and show you how to run it.

What output tells you the agent is working well

  • The Root Cause section names a specific file and function, not a vague description.
  • The Confidence score is 0.7 or above. Below 0.5 means the agent wasn't sure enough to propose a fix.
  • The Evidence section cites real file paths and line numbers that you can verify.
  • The Briefing Warnings section in briefing.md is empty or mentions only minor issues.
  • Agent 1a used fewer than 30 turns (visible in cost_summary.json). More turns = the agent was hunting around and may not have found a clear signal.
⚠️
Change carefully: things to watch for
If the report says NO_FIX with a coherent reason ("the real cause is in a dependency, not this repo"), that is the system working correctly. If it says NO_FIX with a vague reason, try adding more detail to your bug report. Add exact error strings, file paths, version numbers. The briefing collectors pull from whatever you put in the bug report.

How Prompt Files Shape Agent Behaviour

Prompt files are plain text documents. They contain the instructions each AI agent reads before it starts work. Changing a prompt changes how the agent behaves: what it looks for, what it is allowed to do and what it must produce. These are the highest-leverage files in the whole system. The cards below explain what each one currently says and what you might want to change.

Agent 1a
The investigator's rulebook
prompts/investigation.md
What it does

Tells Agent 1a exactly how to investigate: which tools it can use, what format to fill in every single turn (the FINDINGS LEDGER), and the 3 mandatory checks it must pass before calling it done. This is the most impactful file . Changes here directly affect how well the agent finds bugs.

Good things to add

More investigation steps (e.g. always check open issues for related bugs). Stricter self-critique checks. Language-specific hints if you work in Go or Java. Domain-specific evidence patterns your team knows about.

Snippet from the actual file
## Investigation policy Use tools only when the result can change the diagnosis. Preferred order: 1. Read the bug report and briefing. 2. Inspect Error Sources first. 3. Read source files around matching functions. 4. Use Grep only for targeted symbols. 5. Use git history only after identifying likely files. 6. Consider one alternative cause and check it briefly. 7. Stop when confidence reaches 0.70.
⚠️
Watch for: Adding too many mandatory steps slows the agent down significantly. Each extra tool call costs time and money. Keep additions focused on high-signal evidence, not exhaustive checking.
Agent 1a → 1b
How the investigator writes its notes
prompts/investigation_write.md
What it does

After Agent 1a finishes investigating, a separate one-turn call converts its free-text findings into the structured checkpoint.json that Agent 1b reads. This prompt defines the JSON shape, including the critical fix_context field that carries the verbatim current code of the fix location to Agent 2.

Good things to add

Fields that carry important context to downstream agents. For example: an estimated commit range, a list of related functions the developer should also check, or a short "what the developer needs to know" summary.

Snippet from the actual file
`fix_context`: for every function or block identified as the fix location, copy its current verbatim content from the evidence transcript. Include function signature + full body so Agent 2 can write a unified diff with correct @@ hunk markers and context lines.
⚠️
Watch for: If you add new fields to checkpoint.json, also update prompts/diagnosis.md to tell Agent 1b how to use the new fields. Otherwise they are silently dropped.
Agent 1b
The synthesiser's rules
prompts/diagnosis.md
What it does

Agent 1b reads the checkpoint and converts it into a schema-validated JSON verdict. This prompt tells it to never invent files, commits, or functions not in the checkpoint, to preserve confidence, and to cap confidence at 0.4 when upstream evidence was weak.

Good things to add

Extra fields to carry forward to the report (e.g. a "summary for a non-technical reader"). Stricter rules about what qualifies as a concrete file reference vs a vague reference.

Snippet from the actual file
- Do not invent files, commits, functions, or evidence not in the checkpoint. - Preserve uncertainty through confidence fields and unknowns. - If checkpoint evidence is weak, produce a low-confidence diagnosis rather than fabricating.
⚠️
Watch for: This prompt directly controls what travels to Agent 2. If you add permissiveness here (e.g. allowing inference), Agent 2 can end up writing diffs for code that doesn't exist.
Agent 2
The fix-writer's decision rules
prompts/solution.md
What it does

Tells Agent 2 when to write a patch (FIX) vs when to decline (NO_FIX). Sets the unified-diff format rules that make the patch apply cleanly with git apply. Defines how weak evidence must be flagged. The confidence cap,, forced risk level, mandatory reviewer notes.

Good things to add

Language-specific diff conventions (e.g. "for Python, always preserve the indent style of the surrounding function"). Additional reviewer-note requirements for high-risk changes. A rule requiring the agent to name the test that should cover the fix.

Snippet from the actual file
Hunk header format is @@ -start,count +start,count @@ where count is the total number of lines in the hunk. Never write @@ -line,1 +line,1 @@. that is invalid and git apply will reject it.
⚠️
Watch for: Relaxing the NO_FIX conditions causes the agent to produce diffs for uncertain diagnoses. These diffs often don't apply cleanly or fix the wrong thing. More conservative is safer.
Agent 2.5
How to write a regression test
prompts/validation.md
What it does

Tells Agent 2.5 to write exactly one test function that fails on the unfixed code and passes on the fixed code. Sets the output format: a JSON object with test_path, test_diff, and explanation. The test must use the project's existing framework.

Good things to add

Framework-specific conventions for your codebase (e.g. "always use pytest fixtures, never bare assertions"). A naming convention for the test function. A rule requiring the test to have a docstring explaining the bug it covers.

Snippet from the actual file
Write exactly ONE regression test: - The test MUST FAIL on the unfixed code. - The test MUST PASS on the fixed code. - Use the same framework the project already uses. - Write a single test function only. not a class, not a suite. - Do not modify any existing file.
⚠️
Watch for: If you make the test requirements too strict, Agent 2.5 will sometimes fail to produce a valid test and the validation stage will skip the regression test (but still report the existing-suite result).

01
Add a new briefing collector for a new language
Each collector is a self-contained bash script that reads from the environment and writes Markdown to stdout. You can add one for any language, tool, or data source.
  • Create collectors/myname.sh following the pattern in collectors/git.sh
  • Start with printf '## My Section\n\n' and write your data below
  • Register it in scripts/briefing.sh. Find the block where the four collectors are called
  • Run make test-briefing to confirm the new section appears and the pipeline still passes
  • Ask Claude: "Create a collector that traces C++ #include chains for mentioned .cpp files. Follow the pattern in deps.sh."
02
Add a new test framework to detect
The test runner detector reads project config files and returns the correct command. Adding a new framework is just adding a new detection case.
  • Open collectors/testrunner.sh and find the detection block
  • Add a new case: check for the framework's config file (e.g. rspec.yml, phpunit.xml)
  • Write the detected command to $TEST_CMD_FILE
  • Run make test-briefing. The smoke test will check the detection.
  • Ask Claude: "Add PHPUnit detection to testrunner.sh. Config file is phpunit.xml. Command is `./vendor/bin/phpunit`."
03
Strengthen the self-critique checks in the investigator
The 3 mandatory checks before FINAL FINDINGS are the quality gate for diagnosis. Adding a 4th check is the highest-leverage prompt improvement possible.
  • Open prompts/investigation.md and find the "Self-critique" section
  • Add a new numbered check describing what the agent must verify
  • Include the pass/fail criteria so the agent knows when it has satisfied the check
  • Run the real-repo test to compare confidence scores before and after
  • Ask Claude: "Add a 4th self-critique check to investigation.md: the agent must confirm that the fix_context it copied exactly matches what Read returns for that file at the current HEAD."

A note on testing your changes

Every change you make should be verified with the test suite. The pattern is always the same:

  1. Make your change.
  2. Run make lint (catches bash syntax errors instantly).
  3. Run make test (6 minutes, no AI, checks the whole pipeline).
  4. If you changed a prompt or a collector, run make test-real-repo-quick (40 seconds, 2 real bugs, calls AI).
  5. If everything passes, you're done.
The standard change-and-verify cycle
# 1. Make your change (prompt file, collector, or config)
vi prompts/investigation.md

# 2. Syntax check (instant)
make lint

# 3. Full test suite (no AI, ~6 min)
make test

# 4. Quick real-repo check (calls AI, ~40 sec, costs ~$0.40)
make test-real-repo-quick

# 5. Read the latest report to see if quality improved
cat .rca-mas/runs/latest/report.md
