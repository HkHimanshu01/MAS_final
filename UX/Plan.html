Planning philosophy

This plan is designed to survive roadblocks. Each checkpoint is independently presentable — you never need to "finish everything" to show progress. The ordering follows impact ÷ effort, with hard dependencies resolved first.

Checkpoint 1

The floor — always shippable

If every roadblock hits — unfamiliar codebase, CSS fights, unexpected dependencies — you still walk into the MD meeting with these done. Each Phase 2 item is independent; skip any one and the rest still work.

Budget: ~9h of work + 1h buffer = 10h across 5 days. Commit to this. Everything past this is upside.
Phase 0 · Orient · Days 1–2

Read codebase + capture before state

~2–3h Non-negotiable
What to do

Map the React project: folder structure, state management, styling approach (CSS modules? Tailwind? styled-components?), data sources (hardcoded? API? files?), component patterns, role/BU selector mechanics. Screenshot every page as "before" state.

Why it matters

Every other change depends on understanding the code. This is where you discover whether data is hardcoded in components (harder) or loaded from files (easier). That discovery determines Phase 1 approach.

Timebox rule

Hard stop at 3h. Even partial understanding is enough to start changes. You'll learn more by editing than by reading. Focus on: homepage component, sidebar component, and wherever pattern/tool data lives.

Roadblock fallback

If the codebase is deeply complex (monorepo, many layers of abstraction), narrow your focus to just the homepage component and sidebar. Those two areas are all you need for the remaining C1 items.

Phase 1 · Data foundation · Day 3

JSON config layer

~2h Non-negotiable
What to do

Create workflows.json, tools.json, prompts.json + helper functions (getWorkflowById, getToolsByCapability, etc.). These are 10-15 line functions over JSON. If the portal already has data files, extend them instead of creating new ones.

UX theory

Not directly visible to users — but it enables every visible change that follows. It's also the "future-proof architecture" slide in the MD presentation. New workflow = new JSON record. No developer needed for content changes.

Code approach

If data is hardcoded in components → create new JSON files in a /data folder and import them. If patterns and tools already come from separate data files → extend that pattern. Either way, UI components should read from data, not contain data.

Claude Code tip

"Here's the schema structure [paste from context doc]. Here's the content for the RFP Response pattern [paste from portal]. Generate the JSON record." Fast and mechanical.

Phase 2 · Quick wins · Days 4–5
Independence rule: Each change below is self-contained. You can do them in any order, skip either one, and the other still works. This protects you from cascading delays.

Label the sidebar icons

~1h Highest impact/effort ratio
What to do

Add persistent text labels below or beside every icon in the left nav rail. If space is tight, expand the sidebar by 40-60px. At absolute minimum, add immediate-show tooltips on hover (no delay).

UX theory

Recognition over Recall (Nielsen Heuristic #6). Icon-only nav forces users to recall what icons mean. Labels let them recognize instantly. Research shows labeled nav outperforms icon-only by 2-3x in enterprise tools with infrequent users.

Code change

Find the sidebar component. Add <span> labels next to each icon. Adjust CSS width/padding. That's it. Possibly the simplest code change in the entire plan.

MD talking point

"Our users visit the portal occasionally, not daily. They can't learn a custom icon language for a tool they use once a week. Labels eliminate guessing."

Homepage — task-first entry cards

~2–3h Very high impact
What to do

Replace the four equal-weight cards with intent-based groupings. Example: "I need to do something" (shows top workflows), "I need a tool" (tools catalog), "I want to learn" (Academy + Playbooks). Reduce from 4+ equi-weighted choices to 3 clear ones with one prominent.

UX theory

Hick's Law: Fewer equi-weighted choices → faster decisions. Jobs-to-be-Done: Users arrive with a goal ("respond to RFP"), not a content preference ("I want a Pattern"). Organizing by intent matches their mental model.

Survey backing

37 respondents (8.7%) said "no clear use case identified" as their biggest barrier. This is directly addressable by organizing the homepage around tasks, not content types. Content generation (82.1%) and research (60.4%) are the top intents — make those prominent.

Roadblock fallback

If full restructure is too complex, even just: (1) make one card larger/prominent, (2) add a subtitle like "Start here" to the most common intent, (3) reorder so the most-used category is first. This delivers 70% of the value with 30% of the effort.

Checkpoint 2

The target — catalog becomes workbench

Budget: ~9h of work + 1h buffer = 10h across days 6–10. This is your ambitious-but-realistic target.

Cross-link patterns ↔ tools ↔ prompts

~2h High impact
What to do

When viewing a pattern (e.g., RFP Response Acceleration), show linked tools (ARC, Proposal Builder) + relevant prompts. When viewing a tool, show which patterns use it. Use the JSON data layer from C1 to connect existing content that's currently siloed.

UX theory

Information Foraging Theory (Pirolli & Card) — users follow "information scent." A dead end ("I found the pattern but now what tool do I use?") kills foraging and the user leaves. Cross-links keep the scent alive.

Code change

The JSON config from C1 already maps patterns → tools → prompts. This is a UI change: add a "Related tools" and "Related prompts" section to pattern detail pages, and a "Used in patterns" section to tool pages. Small component, reads from JSON.

MD talking point

"Before, a user found a workflow pattern and then had to separately hunt for the right tools and prompts. Now, the portal connects everything — find one thing, see everything related."

Upgrade tool/pattern cards with existing metadata

~2h High impact
What to do

The portal already shows rich metadata: setup time (visible as "2h setup"), complexity level, "when to use / when not to use", linked AI tools. But it's buried in expandable sections. Surface the 6 most important decision cues directly on the card face: setup time, complexity, top use case, primary tool, role fit, and "not for" warning.

UX theory

Progressive Disclosure (Lidwell et al.) — show decision-critical info first. The portal already has this data; the problem is surfacing it at the moment of decision rather than after a click. First-Click Testing (Bob Bailey) — 87% task success if first click is correct.

Data source

All from existing portal content — no new data needed. The patterns page already shows: Official/Community badge, Intermediate/Advanced complexity, setup time estimate, linked AI tools (ARC, Proposal Builder, Amethyst), and expandable "when to use / when not to use" sections.

Code change

Modify the card component to show key fields at the card level instead of behind an expand. Pull data from the JSON config. Add 2-3 small chip/badge elements per card. Minimal CSS work.

Hero workflow workspace — RFP Response

~4h Highest complexity Highest impact
What to do

Build a generic WorkflowWorkspace component. Populate it with RFP Response Acceleration (6 steps already defined on the portal: Ingest RFP → Map to capabilities → Human review checkpoint → Draft proposal sections → Win theme layering → Final QA). Stepper UI with expandable steps, direct tool links, prompt templates at each step.

UX theory

This is the core of the Hero Workflows First strategy the MD chose. The biggest portal gap: "catalog, not workbench." Patterns explain workflows but remain read-only. The workspace makes them interactive and launchable — reducing decisions between "I have a task" and "I got a trusted outcome."

Architecture

The workspace shell must be generic — it reads workflow data from JSON and renders any workflow. The RFP content is just the first JSON record. If the MD wants different workflows, swapping is a data change, not a code change. This is the "future-proof" proof.

Roadblock fallback

If full stepper is too complex in time, build a simplified version: an enhanced pattern page with numbered clickable steps, each showing the tool to use + a direct "open in [tool]" link + the prompt to use. Still delivers the "launchable workflow" story without the full workspace component. Ship this, show wireframe for the full one.

This is the hardest item. The 1h buffer specifically protects against this running over. If you're at hour 3 and it's not coming together, switch to the fallback version immediately — an enhanced pattern page is 80% of the value at 40% of the effort.

Roadblock playbook

For each item, the most likely thing that goes wrong and what to do about it. The meta-strategy: if stuck for more than 30 minutes on any single issue, switch to the fallback immediately.

▶ Phase 0: Codebase is more complex than expected High likelihood

What happens: The React project uses unfamiliar patterns (custom hooks, context providers, unusual state management), or the folder structure is deeply nested, or components are tightly coupled.

Mitigation: Timebox at 3h hard. Focus only on finding: (1) the sidebar component, (2) the homepage component, (3) wherever data for patterns/tools lives. You don't need to understand the whole app — just the parts you're changing.

Claude Code tip: "Here's my project structure [paste tree output]. I need to find where the sidebar navigation is rendered and where the homepage cards are defined. Show me the relevant files." Let Claude Code do the exploration.

▶ Phase 1: Data is hardcoded in components Medium likelihood

What happens: Pattern and tool data is directly written inside React components instead of loaded from files or an API. Extracting it means refactoring existing code.

Mitigation: Do NOT refactor existing components. Create new JSON files in a /data folder and import them. Your new components and changes read from JSON; existing components stay as-is. Over time, existing components can be migrated — but not now.

Key principle: Don't fight the existing code. Add alongside it. The JSON layer exists for YOUR new features, not as a refactor of the old ones.

▶ Sidebar: CSS breaks when adding labels Low likelihood

What happens: Adding text labels pushes the sidebar width and breaks the main content layout, or the sidebar uses fixed positioning with hardcoded widths.

Mitigation: Three fallback levels: (1) Expand sidebar by 40-60px and adjust main content margin, (2) If layout is too coupled, use icon-size labels only (abbreviations), (3) At absolute minimum, add instant-show tooltips on hover. Even option 3 is a clear improvement over the current state.

▶ Homepage: Component is too complex to restructure Medium likelihood

What happens: The homepage component has complex state, fetches data from multiple sources, or is deeply nested with other components. A full restructure would take 5+ hours.

Mitigation (70% value for 30% effort): Instead of restructuring, make three small changes: (1) Reorder cards so the most-used category is first, (2) Make one card visually larger/prominent, (3) Add a subtitle like "Most teams start here" to the top card. This delivers the "task-first" story without touching the component architecture.

▶ Hero workflow: Full stepper component is too ambitious High likelihood

What happens: Building a generic WorkflowWorkspace with a stepper UI, expandable steps, tool links, and prompt templates takes more than 4 hours. Component state management gets complex.

Mitigation — simplified version (80% of value): Don't build a stepper. Instead, build an enhanced pattern page: a single scrollable page with numbered sections for each step. Each section shows: step name, description, which tool to use (with a link), the prompt to use, and any "watch out for" notes. This is essentially a styled list — much simpler than a stateful stepper component.

Decision point: At hour 3, assess. If the stepper is coming together, finish it. If not, switch to the simplified version immediately. Either version delivers the "catalog → workbench" narrative.

▶ General: Running out of time before C2 Medium likelihood

What happens: C1 items took longer than expected. You're at day 7 and C1 is barely done.

Mitigation: C1 alone is a presentable story. If you're short on time, skip C2 entirely and spend remaining time on the C3 presentation package instead — before/after screenshots, architecture diagram, roadmap. A polished C1 with a great presentation beats a rough C2 with no narrative.

The frame to use: "Here's what we've built (C1), here's the data supporting each decision (survey), and here's the roadmap for the next iteration (C2 items become 'planned' instead of 'done')."

The 30-minute rule: If you're stuck on any single technical issue for more than 30 minutes, switch to the fallback version. Don't debug CSS layout issues when you could be building the next feature. The fallback versions exist specifically for this — use them without guilt.
