The underlying data already exists in the portal. You're restructuring how it's rendered — not creating new content.

Step flow pills → Interactive step accordion
Evolved
As-is
Horizontal row of colored pills (Ingest RFP → Map to capabilities → … → Final QA) with arrows between them. Below that, a flat numbered list under "STEPS" heading, each with step name, tool badge, and one-line description. All steps visible at once, no state, no interaction.
Aspirational
Vertical accordion list where each step is a row with a status circle (✓ done / numbered current / gray upcoming / ! review). The active step expands to show input checklist, starter prompt, and action buttons. Completed steps show result summaries (e.g., "32 requirements parsed"). Upcoming steps stay collapsed.
UX difference: The current flat list treats all steps equally — the user has to mentally track "where am I?" The accordion gives them visibility of system status (Nielsen's #1 heuristic) and progressive disclosure — only the next actionable step is open, reducing cognitive load.

Net-new features (new components, new data)

These don't exist in the current portal at all. Each requires a new frontend component and — in some cases — new backend fields or services.

Preflight intake panel
New
As-is
Does not exist. User reads the pattern page and then manually opens each tool. No structured context collection before starting.
Aspirational
A form section with 5 fields:

1. Client / Account (text input) — Identifies the engagement. Used to tag the workflow instance and could pre-filter evidence libraries later.
2. Data boundary (dropdown: Accenture internal / Client-permitted / Restricted) — The single most important governance field. Controls which tools are safe to use and what data can flow through.
3. RFP deadline (date picker) — Sets urgency context. Could drive priority nudges later.
4. Review owner (text/people picker) — Assigns who must approve at the human review checkpoint. Turns the review step from policy text into an assigned action.
5. Brief context (optional text) — Free-text for sector, scope, competitive landscape. Helps the system recommend the right prompt pack and evidence.

Submitting creates a workflow_instance record and launches the first step.
UX difference: This is scaffolding — it reduces the cognitive load of "how do I start?" to answering 5 structured questions. It also forces the data-boundary decision upfront (currently buried in policy text), which is the #1 adoption barrier in the surveys. The form also creates a saved context that carries across all 6 steps so the user never re-enters the same information.

Input checklist per step
New
As-is
Does not exist. Each step only has a one-line description (e.g., "Upload RFP document; ARC parses and classifies each requirement section."). User must infer what inputs they need.
Aspirational
Each expanded step shows a checkbox list of required inputs. Items auto-check when prior steps complete (e.g., "RFP parsed ✓" auto-fills when Step 1 completes). Manual items remain unchecked until user confirms. Example for Step 4: RFP parsed ✓, Mapping approved ✓, Evidence linked ✓, Win themes (optional).
UX difference: Checklists are a form of external cognition — they offload "what do I need?" from the user's memory to the interface. They also create a natural gating mechanism: the user sees at a glance whether they're ready to proceed, reducing false starts and errors.

Starter prompt per step
New
As-is
Does not exist on the pattern page. The portal has a separate Prompt Library (48+ prompts on SharePoint) but they're not linked to specific pattern steps. User must navigate away to find relevant prompts.
Aspirational
Each expanded step shows a monospace prompt box with a recommended prompt and a "Copy" button. The prompt is contextual to the step (e.g., Step 4's prompt references the RFP requirements and approved mapping from prior steps). This is the bridge from "I know what to do" to "I know exactly what to type."
UX difference: This closes the discovery-to-execution gap. Currently, the pattern tells you to "draft proposal sections" but doesn't tell you how to prompt the tool. The starter prompt eliminates blank-page paralysis and ensures quality by encoding best practices directly into the workflow. It also reduces cognitive switching — user stays on the workflow page instead of hunting through the prompt library.

Step action buttons ("Open in Tool", "Save & pause")
New
As-is
No action buttons on step rows. The tool tags (ARC, Proposal Builder) are displayed but not clickable launch links. User must manually open the tool in a separate tab.
Aspirational
Two buttons per active step: "Open in [Tool] →" (primary, launches the linked tool) and "Save & pause" (secondary, saves progress and returns user to My Space). The "Open in Tool" button carries context from the preflight (client, data boundary) into the tool if possible.
UX difference: This is the single most important change for turning a pattern from "reading" into "doing." A visible call-to-action at the point of decision eliminates the handoff friction. "Save & pause" supports enterprise reality — work spans multiple sessions. Together, these buttons increase pattern-view-to-start rate (the key metric for this area).

Review gate banner
New
As-is
"Human review checkpoint" is just another step pill in the flow and a row in the numbered list. No assignment, no tracking, no notification. Reviewer requirement is implied by the step description text only.
Aspirational
An amber-highlighted banner between the relevant steps showing: reviewer name + avatar, assignment timestamp, notification status ("Notified via Teams"), current state (Pending / Approved / Changes requested), and a "Nudge reviewer" action. Blocks progression to the next step until approved.
UX difference: This turns governance from invisible policy into visible product behavior. The current portal's #1 adoption barrier is data restriction uncertainty — making review explicit and trackable builds trust. It also prevents unsafe progression (drafting client-facing content before someone checks the AI mapping). The banner is an explicit trust affordance.

Trust & governance sidebar panel
New
As-is
Trust signals exist but are scattered: "★ Official" pill on the card, "low risk" on tool cards, "Do not use ARC with Restricted data" buried in the "when not to use" text. No consolidated trust view.
Aspirational
A persistent sidebar panel with 5 rows: Approval status (Approved), Data boundary (set from preflight), Review requirement (Yes — before delivery), Risk level (Low risk), Last verified date (Apr 18, 2026). Always visible while the user works through steps.
UX difference: Trust cues need to appear at the moment of use, not just at the moment of reading. A persistent sidebar means the user never has to wonder "wait, is this okay for my data?" mid-workflow. This directly addresses the calibrated trust research — users are more confident and more compliant when governance is transparent rather than hidden in policy documents.

Linked assets sidebar panel
New
As-is
Tool tags (ARC, Proposal Builder, Amethyst) are shown but prompts, evidence libraries, and training modules are on entirely separate portal pages. User must navigate to 3–4 different sections to gather everything for one workflow.
Aspirational
Sidebar lists all linked assets in one place: tools (Proposal Co-pilot, ARC), prompt packs (RFP Prompt Pack — 6 prompts), evidence libraries (FS Evidence Library — 142 items), and training (Proposal Writing module). Each item is clickable and opens the relevant portal page or tool.
UX difference: This is the unified topic page concept — instead of the user being the librarian assembling materials from 5 different shelves, the portal becomes the librarian handing them a complete kit. Reduces navigation depth from 3–4 clicks to 0 (everything is visible on the page they're already on). Directly reduces cognitive load and increases content discovery breadth.

Time saved estimator + progress tracker
New
As-is
No progress tracking. No value signal. User has no sense of how far along they are or what benefit the workflow is providing. The "2h setup" badge is the only time-related cue.
Aspirational
Two sidebar elements: (1) Progress bar — "3 of 6 steps done · 50% · ~45 min left." Based on workflow_instance_step completion status. (2) Time saved banner — "~6.5 hrs saved" based on team benchmarks for this workflow. Initially a static estimate from content metadata; later can be calculated from actual step durations.
UX difference: The progress bar is visibility of system status — critical for multi-session work. The time-saved banner addresses UTAUT's performance expectancy: it turns the abstract "AI saves time" into a concrete personal number. This is the same mechanism that makes fitness trackers sticky — visible, quantified progress toward a valuable outcome.
